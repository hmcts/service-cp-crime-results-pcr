# 001. New pull-based API Marketplace channel for Prison Court Register data

**Status:** Accepted, 16 Jul 2026
**Jira:** AMP-888 — parent epic for this PCR API (AMP-889 event ingestion, AMP-890 data
modelling, AMP-891 PII redaction/encryption are child tickets under this decision)
**Design docs:** [`2026-07-16-pcr-api-marketplace-design-v2.md`](../../designs/2026-07-16-pcr-api-marketplace-design-v2.md)
is the full architecture this ADR authorises; every other design doc in this repo (stateless
proxy, data store, hearing event ingestion, orchestrator) is a deep-dive expansion of one
section of it.

## Context

Prison Court Register (PCR) source data exists today only as a PDF, generated by a legacy
pipeline (Function App → Progression → Docmosis) and distributed by email/post to whichever
recipients each hearing's NOW subscriptions resolve to. API Marketplace subscribers (HMPPS and
prisons) have no programmatic access to this data — only the PDF distribution channel exists.

Per `hmcts-standards.md`, any integration pattern not previously used (a new pull-based Query
API alongside an existing push/callback pipeline) and the creation of a new public repo pair
both require an ADR before proceeding.

## Decision

Build a new read channel — `api-cp-crime-results-pcr` (OpenAPI spec) +
`service-cp-crime-results-pcr` (Spring Boot service), Modern-by-Default pattern — that exposes
the same underlying PCR content via a pull `GET` API, without replacing or rebuilding anything
already working:

- **Not a replacement for the existing email/post distribution.** The legacy pipeline keeps
  running unchanged; this is an additional channel.
- **Does not rebuild subscriber management.** `service-cp-crime-hearing-results-document-subscription`
  and `now_subscriptions` keep owning subscriber registration and push notification —
  `VocabularyService`/`PrisonCourtRegisterSubscriptions` are read, not ported (design doc §5b/§14).
  This service's Query API URL is wired into that service's existing callback payload.
- **One PCR per `(hearingId, defendantId)`, never merged across defendants** — matches how
  today's PCR generation already works (`SetPrisonCourtRegister` builds one fragment per
  defendant per hearing) and is load-bearing throughout every layer of this design (decision
  engine fan-out, data-store keying, Query API shape).
- **Event-driven ingestion, not synchronous generation on request** — triggered by the same
  Azure Event Grid `Hearing_Resulted` notification the legacy Function App already listens to
  (see ADR-002/AMP-889 for the ingestion mechanics).
- Scaffolded from `api-hmcts-crime-template`/`service-hmcts-crime-springboot-template`, the
  standard template pair for a new API Marketplace capability — no deviation from the template
  needing its own ADR.

## Consequences

- Two new public repos exist that didn't before, each requiring the standard HMCTS repo-ownership
  and coding-in-the-open process (`hmcts-standards.md`).
- This service now sits downstream of `cpp-context-results`' source-propagated id (design doc §7)
  and Redis cache, and upstream of the existing subscription/callback infrastructure — a new
  dependency surface in both directions that didn't exist before this decision.
- Every subsequent design/ADR in this repo (stateless proxy, data store, hearing ingestion,
  orchestrator, PII carriage) is scoped *within* this decision, not a re-litigation of it.

## Alternatives considered

- **Extend the legacy Function App/Docmosis pipeline with a pull endpoint** — rejected; that
  pipeline is PDF-generation-shaped (Durable Functions, Docmosis templating), not a fit for a
  versioned, queryable REST resource, and API Marketplace services are Modern-by-Default
  Spring Boot, not legacy Function Apps.
- **Have HMPPS/prisons parse the existing PDF output** — rejected; not machine-readable, not a
  contract, and not what API Marketplace subscribers were asking for.

## Compliance notes

- This data is OFFICIAL-SENSITIVE case/hearing/party data — the API Marketplace's standard
  classification applies from day one (`hmcts-standards.md`).
- Both new repos are public by default per MoJ/HMCTS coding-in-the-open policy; no private-repo
  case was identified.
